# PM 工作流

> 本文档面向「产品经理 / 项目经理 / 业务方」。如果你只负责测而不负责管，请看 [QA 测试人员工作流](./tester-workflow.md)。

---

## PM 在 casemap 里做什么？

PM 在 casemap 里是「数据拥有者」 — 你创建项目、上传接口、邀请测试人员、看数据、导出报告。测试人员负责标状态，你负责看全局。

---

## 1. 创建项目（第一步）

### 步骤

1. 打开浏览器访问 `http://服务器IP:8765`
2. 看到 casemap 首页（首次访问是空白的）
3. 点击右上角 **「New Project」**（新建项目）
4. 在弹窗里填：
   - **Project name**（必填）：项目中文名，比如「订单系统 v2」「支付重构」「登录注册升级」
   - （可选）**Description**：项目说明，会显示在项目详情页
5. 点 **「Create」**（创建）

<!-- TODO: screenshot of new project form -->

### ⚠️ 创建后立刻要做的事

页面会弹出一个**只显示一次**的对话框，显示你的 API Key（大约 40+ 字符的长串）：

```
┌─────────────────────────────────────┐
│  ⚠️  Save this key now              │
│                                     │
│  sk-casemap-7f3a9b2e8c1d4f5a6b7c... │
│                                     │
│  This key won't be shown again.    │
│  Copy it before closing this.       │
└─────────────────────────────────────┘
```

**你要做的：**

1. **立刻复制**到公司密码管理器 / 加密文档
2. **截图保存**也行
3. 关闭弹窗

**绝对不要：**

- ❌ 截图发到朋友圈 / 微博 / GitHub
- ❌ 发到公开群
- ❌ 关闭弹窗后问"刚才那串字符呢" — 它不会再次显示

**类比**：API Key 就是你家的门钥匙 — 谁拿到谁就能进门。发给需要的人，不要外传。

## 2. 上传接口列表

### 步骤

1. 进入项目后，点 **「Upload Spec」**（上传接口文档）
2. 选择你的接口文档文件
3. 等 5–30 秒（看接口数量）
4. 看到脑图生成完毕

### 接口文档要求

| 格式 | 后缀 | 来源 |
|------|------|------|
| OpenAPI | `.json` 或 `.yaml` | Swagger Editor 导出 / 后端开发导出 |
| Swagger | `.json` 或 `.yaml` | 同上 |
| Postman v2.1 | `.json` | Postman → Export |
| Apifox | `.json` | Apifox → 导出 OpenAPI |

<!-- TODO: screenshot of file picker with supported formats -->

**怎么拿到这个文件？**

- 让开发从 Swagger / Apifox / Postman 导出
- 文件大小一般几 KB 到几 MB（接口数量决定）

**如果开发说「我们接口文档是 Word / 写 Confluence 上的」怎么办？

**让开发重新导出一份 JSON** — 这是 casemap 唯一支持的格式。Word 和 Markdown 暂时不支持。

### 上传后看到什么？

- 项目里多了一个 spec（接口文档版本）
- 自动生成了一张脑图
- 脑图上有节点（每个节点 = 一个测试用例）
- 节点数量取决于接口数量 — 通常几十到几百个

### 多个版本

接口文档更新后（比如开发改了接口），你可以**再上传一份新的**：

- casemap 会保留历史版本（每次上传是新版本）
- 你可以选「以哪个版本为准」生成脑图
- 已经标过的测试结果会保留（casemap 用 stable_id 匹配）

### 发给测试人员什么？

## 4. 看进度页面（你最爱的页面）

进度页面是 PM 用得最多的页面 — 一目了然看整个项目的测试状态。

### 怎么进

在脑图页面左侧导航点 **「Progress」**（进度），或者地址直接 `/projects/{项目ID}/progress`。

<!-- TODO: screenshot of progress dashboard -->

### 数字怎么看

页面顶部显示 6 个数字：

```
总计 245  通过 180  失败 12  进行中 20  阻塞 5  跳过 8  未测 20
```

| 字段 | 业务含义 | 你应该关心什么 |
|------|---------|---------------|
| 总计 | 这个项目一共多少条测试用例 | 看规模 |
| 通过 | 测试员已经测完且全部符合预期 | 看进展 |
| 失败 | 测试员测了但有 bug | 看风险 |
| 进行中 | 测试员正在测但没测完 | 看活跃度 |
| 阻塞 | 暂时没法测（缺环境、缺账号） | 看是否能解决 |
| 跳过 | 主动选择不测 | 看理由是否合理 |
| 未测 | 还没人测 | 看剩余工作量 |

### 完成率怎么算

```
完成率 = 通过数 / 总数 = 180 / 245 = 73.5%
```

**但注意**：完成率高 ≠ 项目可以上线！

- 73.5% 完成率 + 12 条失败 → **不能上线**，要先修 bug
- 73.5% 完成率 + 0 失败 + 27 条阻塞 → **还要看阻塞原因**，如果是 P0 阻塞也不能上

### 饼图怎么看

饼图每个色块 = 一个状态的占比。色块大小 = 该状态占总用例的比例。颜色对应：

- 绿色 = 通过
- 红色 = 失败
- 蓝色 = 进行中
- 黄色 = 阻塞
- 紫色 = 跳过
- 灰色 = 未测

<!-- TODO: screenshot of donut chart with legend -->

### 按接口 / 标签看（细分维度）

页面中下部通常有「按接口路径分组」的横条图：

```
/login        ████████████░░░░░  92% (23/25)
/register     ██████████████░░░  85% (17/20)
/order        ██████░░░░░░░░░░░  50% (30/60)
/refund       ✓✓✓✓✓✓✓✓✓✓✓ 100% (12/12)
```

**怎么看：**

- 一眼看出**哪个模块进度最慢**（横条最右边还有灰色）
- 一眼看出**哪个模块 100% 测完**（横条全绿，可以收尾）
- 一眼看出**哪个模块失败最多**（红色横条，PM 要去催开发）

## 5. 看失败用例

### 怎么进

进度页面下方有「Failed Cases」（失败用例）清单，或者点左侧导航 **「Cases」** → 筛选「Failed」。

<!-- TODO: screenshot of failed cases list -->

### 失败清单里有什么

每一条失败用例显示：

- 接口路径 + 用例标题
- **失败备注**（QA 写的「实际看到了什么」）
- 失败时间

### 怎么用失败清单

1. **复制到 ticket 系统**：把失败用例 + 备注复制到 Jira / 飞书 / 禅道
2. **按模块分发**：分给对应的开发
3. **优先 P0 / P1 的**：先修最重要的
4. **跟开发对齐**：开发说「不是 bug，是 QA 测错了」时，让 QA 复核

## 6. 导出报告

### 给开发 / 老板的「漂亮报告」

1. 在进度页面 / 脑图页面，点 **「Report」** 链接
2. 看到一张干净、只读的报告页
3. 三种导出方式：
   - **下载 HTML**：适合邮件附件
   - **打印 PDF**：适合提交给上级
   - **截图**：适合发 IM

## 7. 权限管理（v1 简化版）

casemap v1 的权限模型很简单 — 一个项目一个 API Key，谁拿到谁就有完全权限。

### 当前能力

| 操作 | 谁可以做 |
|------|---------|
| 查看项目 | 任何拿到 API Key 的人 |
| 改测试状态 | 任何拿到 API Key 的人 |
| 上传新 spec | 任何拿到 API Key 的人 |
| 删除项目 | 任何拿到 API Key 的人 |

### 简单粗暴的实践方法

| 角色 | 给不给 API Key |
|------|---------------|
| QA 测试人员 | ✅ 给（这是主要用户） |
| 开发（接入 CI 上报） | ✅ 给（用专用 key 更好，见下） |
| 老板 / 业务方 | ✅ 给（只读目的） |
| 外包 / 临时测试 | ⚠️ 临时用，用完收回（v1 不能强制过期，见 [开发怎么用 - 重新生成密钥](./dev-workflow.md)） |

### 未来（v1.1+）

v1.1 将引入：

- 用户登录（不是仅用 API Key）
- 只读 vs 读写 权限分离
- 每条用例的审计日志（谁标了 + 何时）

详见 [根 README - 路线图](../../README.md#roadmap)。

## 8. PM 的日常 checklist

### 项目启动时

- [ ] 创建项目
- [ ] 安全保存 API Key
- [ ] 让开发导出接口文档 JSON 并上传
- [ ] 确认脑图生成正确（接口数 / 用例数符合预期）
- [ ] 邀请测试人员（带 API Key）
- [ ] 在群里通知大家项目启动

### 项目进行中

- [ ] 每天早上看一眼进度页面（5 分钟）
- [ ] 关注失败数变化（修复后应该下降）
- [ ] 关注阻塞数（解决阻塞是 PM 的责任）
- [ ] 阶段性导出报告（每周 / 每两天）

### 项目收尾时

- [ ] 看完成率（应该 100%）
- [ ] 看失败用例（应该 0）
- [ ] 看阻塞用例（应该都解决或放弃）
- [ ] 导出最终报告存档
- [ ] 关闭项目（v1 不支持，v1.1+ 支持）

## 9. PM 跟不同角色怎么沟通

### 跟测试人员

- 阶段性看进度，定时 review 失败清单
- 失败备注不清晰的让测试员补充（不要替 QA 改）
- 阻塞用例帮 QA 协调资源（账号 / 环境 / 文档）

### 跟开发

- 失败用例清单要 **及时分发**（不要攒一周才发）
- P0 / P1 失败标星号
- 开发修了 bug 后，让 QA **复测**，不要凭备注就勾上「通过」

### 跟老板 / 业务方

- 进度页面截图 + 一句话总结（不要甩完整报告）
- 失败数 / 阻塞数变化趋势图（老板只关心「趋势向上还是向下」）
- 重大 bug 当面沟通，不要只发 IM（避免误读）
